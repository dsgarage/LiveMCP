# ミュージシャン目線での UX 検証

ここまでの実装（M4L 版ブリッジ、Remote Script 検証、`.als` 生成）を、
「音楽家が日常に使えるツール」という基準で見直した記録です。
Hard Drops パックの配置を実際にこの仕組みでやった経験（Issue #2）を素材にしています。

## 前提の確認: このツールの UI は会話である

LiveMCP の操作面は Claude との会話です。「パックを並べて」と言えば並ぶ、が理想形で、
実際にそこは成立しました。408 ファイルの配置は一言の依頼で完了しています。

問題はその周辺です。**会話の外側にプログラマーの道具が漏れ出しています。**
セットアップ、更新、`.als` の生成、事故からの回復 — ここに npm、ターミナル、
ポート番号、`--force` フラグが顔を出します。音楽家の日常はここで途切れます。

## 旅程で見る摩擦

| 場面 | 今の体験 | 音楽家にとっての問題 |
|---|---|---|
| 初期設定 | `npm run install-device` → デバイスをドラッグ → Remote Script 導入 → 環境設定で Control Surface 選択 → Live 再起動 | ターミナル必須。手順が 5 つ。名前が `LiveMCP_Probe`（開発用語） |
| 日常（セットを開く） | M4L デバイスを**そのセットに**載せないと動かない | セットごとの儀式。忘れると無反応で、理由も表示されない |
| 日常（依頼する） | 会話で完結 | ここは良い |
| `.als` 系の操作 | `node scripts/als-group.js <パス> ...` | 音楽家は絶対に打たない |
| 生成結果を見る | Finder からダブルクリックで開き直す | 「どのファイルが最新か」を自分で追う必要がある |
| 事故（ブリッジ停止） | 無反応。原因はターミナルやログでしか分からない | Live の画面に何も出ない |
| 更新 | `npm run install-device` + Live 再起動 | ターミナル必須 |

## 発見（音楽家の目で見たもの）

### 1. Control Surface という置き場は、実は正しい — 問題は名前と導線

ご指摘の「日常的に操作する場所ではない」はそのとおりです。ただし性質を分けると:

- **選択は 1 回だけ**。環境設定に触るのは初期設定のときだけで、以後は全セットで常駐する
- 対して M4L デバイスは**セットごとに**載せる必要がある。日常の摩擦はむしろこちらが大きい

つまり Remote Script 化（#14）は「環境設定に 1 回」で「セットごとの儀式ゼロ」に交換する変更で、
音楽家目線では改善方向です。直すべきは:

- 名前を `LiveMCP` にする（`_Probe` は検証用の開発用語）
- 初期設定を「Claude に頼めば選択以外すべて終わる」1 手順にする。
  Control Surface の選択自体は Live に API が無く自動化できないため、
  ここだけは案内文付きの手作業として残す
- 移行完了後は M4L デバイスを廃止する。トラックを 1 本塞ぐ「LiveMCP」も消える

### 2. `.als` 生成を会話に取り込む

`als-group.js` は配管であって UI ではありません。MCP ツールとして露出させ、
「OS トラックをグループにまとめて」で完結させます。

- Live で開いている場合の確認も、`--force` フラグではなく会話でやる
  （「今開いているセットです。先に閉じますか、それとも別名で書き出しますか」）
- 生成後は `open -a "Ableton Live 12 Suite" <生成した.als>` で Live に渡す。
  未保存の変更があれば **Live 純正の保存ダイアログ**が出るので、
  「保存するかどうかの判断は Live の画面で人間がする」という方針とも一致する（要実機確認）

### 3. ファイルの増殖を止める

検証の過程で `Hard Drops.als` の変種が 4 つできました
（無印 / grouped / generated / loops）。どれが正か、音楽家が追うべきではありません。

- 生成物の命名を 1 規則に固定する（例: 常に `<元名>.als` を置き換え、直前の状態は
  Live 純正の `Backup/` に任せる。別名が要るのは比較検証のときだけ）
- 今回の 4 つは検証データとしての役目を終えたら整理する

### 4. Drum Rack「101 パッド半音並び」は網羅であって音楽ではない

Basses 101 個を C0 から半音で並べると、鳴らしたい音を探す時間の方が長くなります。
参考にした Ambient TRACK Project の実物は 1 ラック 4〜25 パッドで、
KICK / SNARE / HATS と**楽器別**に分かれていました。網羅はプログラマーの本能で、
演奏性は音楽家の本能です。

- ドラム系: ファイル名の楽器プレフィックス（`HD_Clap_` / `HD_Kick_` …）で
  ラックを分ける選択肢をデフォルト側に
- ベース・メロディ系の**トーナル素材**: 101 パッドより「1 サンプルを鍵盤全域で弾ける
  Simpler」の方が演奏に向く。キー付きファイルはルート音を合わせて張る
- どう並べるかは好みが分かれるので、配置前に一言確認するのが正しい振る舞い

### 5. Live の画面に「生きている」ことを出す

今回ステータスバー通知（#15）を入れたのは正しい方向で、本実装では次まで広げます。

- 起動時: 「LiveMCP: 準備完了」
- クライアント接続時: 「LiveMCP: Claude が接続しました」
- 長い処理: 開始と完了を出す（「300 パッドを構築中…」「完了（Cmd+Z で戻せます）」）
- 無反応のとき音楽家が見る場所は Live の画面。そこに出ないものは存在しないのと同じ

### 6. 更新も会話で

「LiveMCP をアップデートして」→ Claude が導入スクリプトを実行 →
「Live を再起動してください」だけを返す。ターミナルの操作を音楽家に見せない。

## うまくいっているもの（変えない）

- **勝手に保存しない**方針。作品の確定は人間の判断、はそのまま
- 一括操作が **Cmd+Z 1 回**で戻ること。音楽家の言語で「安全」を意味する
- ブラウザからのドラッグでデバイスを入れる導入手順（Live ネイティブの操作）
- トラック名・グループ名などの成果物が、参考プロジェクトの流儀に揃っていること
