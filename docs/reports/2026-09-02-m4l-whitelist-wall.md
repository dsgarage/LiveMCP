# M4L ホワイトリストの壁

Ableton Live の中で完結する MCP サーバーを作る過程で、Max for Live 経由では保存もグループ化もできないことが分かりました。
Live の制約だと思っていたものが、経路の制約だったと突き止めるまでの記録です。

| | |
|---|---|
| 期間 | 2026-08-26 → 2026-09-02 |
| 環境 | Ableton Live 12.4.5 Suite / Max 9.1.4 |
| 結論 | ブリッジを MIDI Remote Script へ移行する |
| 関連 | Issue #1（完了） / #2（継続） / #9（完了） / #12（起票） |

## 前提

LiveMCP は Ableton Live の中で完結する MCP サーバーです。外部プロセスを立てず、Max for Live デバイスの中に置いた
`node.script` が HTTP で MCP を待ち受け、LiveAPI の操作は `js` オブジェクトのブリッジへ委譲します。
`node.script` からは LiveAPI に直接触れないため、この二段構えが必要でした。

```
MCP クライアント ──▶ node.script ──▶ deferlow ──▶ js ──▶ [ホワイトリスト] ──╳── Live Python API
   Claude Code        HTTP :3360               LiveAPI ブリッジ              save / group_tracks / browser
```

LiveAPI は low-priority thread でしか生成できないため、`node.script` と `js` の間には `deferlow` が必須です。
この構成自体は最後まで正しく動きました。問題はその先にありました。

最後の壁の存在に気付くまでに、その手前の 3 段が全て別々の理由で壊れていました。

## 経過

### 1. v8 は Live の中で存在しなかった（Issue #9）

当初ブリッジは `v8` で書いていました。Live 上ではエラーも出ないまま無応答になります。
原因は外部オブジェクトの読み込みタイミングでした。

`v8.mxo` は `C74/extensions/` にあり Max アプリの起動時にしか読み込まれません。
対して `js.mxo` は `C74/externals/` にあり、オブジェクトが参照された時点で読み込まれます。
Live に組み込まれた Max ランタイムでは `v8` のクラスが登録されず、パッチのコードが繋がらないため
メッセージがどこにも届きませんでした。

ファイルの有無では判断できません（`v8.mxo` 自体は Live 同梱の Max にも存在します）。

### 2. js に変えても Live の中では動かなかった（Issue #1）

`js` へ切り替えても症状は変わりませんでした。Max 単体で同じ `.amxd` を開くと動くのに、Live 上では沈黙します。
切り分けの決め手は Max for Live のログでした。

```
~/Library/Application Support/Cycling '74/Max 9/Logs/MaxPlugLib.log
```

**Live 上のデバイスからは `.amxd` と同じフォルダが Max の検索パスに入りません。**
`js` も `node.script` もスクリプトを検索パスから解決するため、どちらもファイルを見つけられずにいました。
Max 単体では `.amxd` のフォルダが検索パスに入るので動いてしまう、という食い違いもこれで説明が付きます。

スクリプトを `~/Documents/Max 9/Library/` にも配置して解決しました。
`js` が先に復旧し、`node.script` はプロセスマネージャ（N4M PM）だけが起動して子プロセスが無い状態が
残っていたため、バンドルも同じ場所に置いて開通しました。

### 3. 成功したことにするコードを潰した

開通後、未検証だった 3 つのツールを実機で確認しました。
`create_audio_clip` と `replace_sample` は問題なく動きましたが、
`insert_device` は **挿入に失敗しても成功を返していました**。

LiveAPI の `call` は成功時に `["id", <n>]` を返し、失敗しても例外を投げず id 0 を返すだけです。
戻り値を見ずに固定で成功にしていたのが原因でした。オーディオトラックに Simpler を挿そうとした場合などが該当します。
戻り値の id を検証して例外にし、回帰テストを追加しました。

### 4. 実務に投入した（Issue #2）

購入したサンプルパック（408 ファイル）をプロジェクトへ並べる作業に使いました。
1 件ずつブリッジを往復すると 1500 回以上になるため、js 側でループする一括ツールを実装しています。

| 対象 | 件数 | 配置先 | 所要 |
|---|---|---|---|
| ループ | 108 | オーディオトラック 7 本 / シーン 30 | 2.6 秒 |
| ワンショット | 300 | MIDI トラック 7 本の Drum Rack（C0 から半音） | 数分 |

Drum Rack のパッドは LOM から組めることが分かりました。
`RackDevice.insert_chain` でパッドを追加し、`DrumChain.in_note` で音程を決め、
チェーンに `Simpler` を挿して `replace_sample` を呼びます。失敗はゼロでした。

### 5. そこで壁に当たった

配置は完全に自動化できたのに、**最後の 2 つだけが手作業として残りました**。
トラックの Group 化と、セットの保存です。どちらも LOM の関数一覧に存在しません。
加えて、408 件の一括操作が Undo 履歴に 408 件積まれます。

この時点では、この 2 つを「アーキテクチャの限界」として扱いました。
**後から見ると重み付けを誤っています。** 直前の作業で最後に詰まった 2 つを、
そのまま最重要の制約に格上げしてしまいました。

落ち着いて見れば、保存はむしろ人間に残すべき操作ですし
（エージェントが黙ってセットを上書きするのは便利さより事故が大きい）、
グループ化は見た目の整理で機能を塞いでいません。
本当に効いていた制約は、この時点では気付いていなかった
**ブラウザに触れないこと**（プリセット・ラック・プラグインが一切使えない）でした。

### 6. C++ の外部オブジェクトを検討し、却下した

ネイティブの外部オブジェクトを書けば壁を越えられるのではないか、という案を検討しました。結論は否です。

Max の外部オブジェクトがリンクするのは Max SDK であって、Live の内部ではありません。
Live が Max for Live に見せている API は LiveAPI ただ 1 本で、外部オブジェクトを書いてもその壁は動きません。
得られるのはネイティブ性能（今のボトルネックは Live 側の LOM 呼び出しであり、JS ではないため無意味）と、
プロセス内での macOS 自動化だけです。

なお Live は `com.apple.security.cs.disable-library-validation` 付きで署名されているため、
自作の `.mxo` を読み込ませること自体は可能でした。使うとしても最後の手段です。

### 7. 壁の正体は経路の制約だった

LOM の関数一覧に無い関数を、それでも呼んでみるという実験をしました。
結果は明確でした。有効な呼び出しは値を返し、無効な呼び出しは例外ではなく `0` を返します。

| 呼び出し | 戻り値 | 判定 |
|---|---|---|
| `live_app get_document` | `["id", 1]` | 通る |
| `live_set group_tracks` | `0` | 露出していない |
| `live_set save_current_set` | `0` | 露出していない |
| `live_app save` | `0` | 露出していない |

呼び出し経路そのものは生きています。では実装は無いのか。
Live 本体のバイナリを見ると `group_tracks` や `save_current_set` の文字列が実在し、
Push 3 に同梱されている Live API のモデル定義
（`Push3.app/Contents/Resources/python/live_model/Live/`）に決め手がありました。

```
Live.Song        group_tracks, save, can_be_saved,
                 begin_undo_step, end_undo_step, all_tracks, file_path
Live.Application browser
Live.Browser     load_item, preview_item
```

ここから「実装は Live の Python API に存在する。M4L の LiveAPI がホワイトリスト方式で
その一部しか露出していないだけだ」と推定しました。**この推定は後の実機検証で半分外れます**（第 8 節）。

### 8. 実機で確かめたら、推定は半分外れた

Remote Script を書いて Live 12.4.5 で実際に動かしました。

| # | 検証項目 | 結果 |
|---|---|---|
| 1 | 自作 Remote Script がロードされるか | ✅ |
| 2 | `Song.group_tracks` | ❌ **存在しない** |
| 3 | `Song.save` | ❌ **存在しない** |
| 4 | `Application.browser` からロードできるか | ✅ Drum Rack のロードに成功 |
| 5 | Remote Script 内でソケットを開けるか | ✅ Live プロセス内で LISTEN |
| 6 | `begin_undo_step` / `end_undo_step` | ✅ 2 操作が 1 Undo にまとまる |

```
AttributeError: 'Song' object has no attribute 'group_tracks'
AttributeError: 'Song' object has no attribute 'save'
```

`Song` の実メンバーは 245 個あり、保存・グループ関連は `file_path` しかありません。
Push 3 の `live_model` は Push 自身のアプリ向けのモデルで、Remote Script の実行時 API とは一致しません。
**モデル定義を API の一覧として読んだのが誤りでした。**

一方、収穫もありました。**ブラウザが完全に開きます。**

```
Browser: instruments, audio_effects, midi_effects, drums, sounds, clips,
         plugins, max_for_live, packs, legacy_libraries, current_project,
         load_item, preview_item, hotswap_target, filter_type
```

M4L では原理的に触れなかった領域です。`load_item` が使えると、
`insert_device` の「名前でネイティブデバイスを挿すだけ」という制約が外れ、
プリセット・`.adg` ラック・プラグイン・Max for Live デバイス・パック内の音源を名前で読み込めます。

Undo も確認できました。`begin_undo_step` 〜 `end_undo_step` で囲んで
MIDI トラックを 2 本作り、Cmd+Z を 1 回押すと 2 本とも消えました（18 本 → 16 本）。
408 件の一括配置を 1 手で戻せるということです。

開発上の注意も 1 つ分かりました。**Remote Script のコード変更は Live の再起動が必要です。**
Control Surface を入れ直すと `create_instance` は呼び直されますが、
Python のモジュールが `sys.modules` に残るため、更新したファイルは読み直されません。

### 9. グループ化は .als 側で解決した

Live の Python API にも `group_tracks` が無い以上、LOM 経由の道は閉じています。
そこでファイルを書く側から実現しました。

スキーマは推測していません。Live に一度グループ化させた `.als` と元の `.als` を突き合わせ、
そこから規則を読み取っています。

- `GroupTrackSlot` はシーン数と同数
- `ClipSlot`（FreezeSequencer）もシーン数と同数
- `TrackSendHolder` はリターン数と同数。1 つにつき id を 2 個消費
- id は `NextPointeeId` から文書順に連番で確保し、使い切った次を書き戻す
- 子の `TrackGroupId` に親の Id を入れる（親は子を列挙しない）
- 子の `AudioOutputRouting` を Main からグループへ向け直す

**最後の 1 つは差分を取って初めて気付きました。** 実装漏れのままだと、
トラック一覧の見た目は正しいのに音がグループを通らず Main へ直接出ます。
突き合わせをしていなければ見逃していました。

グループ無しの `.als` から生成した結果を Live の出力と比較したところ、構造上の差分はゼロでした
（残る差は元ファイル由来の `TakeId` 正規化、Live が全体で振り直す `NamedRemoteableKeyMidi`、UI 状態のみ）。
生成した `.als` を Live で開くと、`ONE SHOTS` がグループ親、7 本がグループ内として認識されました。

## 決定

**ブリッジを MIDI Remote Script（Python）へ移す。**

Remote Script は Live の Python インタプリタの中で動き、`Live` モジュールの実体に直接触れます。
M4L の proxy を経由しないため、ホワイトリストの手前ではなく向こう側に立てます。
Live 12.4.5 の Remote Script は **Python 3.11** で動きます（同梱 `.pyc` のマジックナンバーで確認）。

移行の根拠は当初考えていた「保存とグループ化ができるから」ではありません（実際できませんでした）。
実測で確かめられた次の 3 点です。

| 操作 | 現在（M4L + js） | Remote Script |
|---|---|---|
| ブラウザからの読み込み | 不可 | `Browser.load_item`（機能の天井が外れる） |
| 常駐 | トラックにデバイスが必要。セットを切り替えると死ぬ | Live 起動時から常駐 |
| Undo | 一括操作が件数ぶん積まれる | `begin_undo_step` / `end_undo_step` で 1 手 |
| `deferlow` | 必須 | 不要 |
| セットの保存 | 不可 | **不可**（Python API にも無い） |
| トラックの Group 化 | 不可 | **不可**（`.als` 生成で解決） |

保存については、できないことをそのまま制約として受け入れます。
エージェントが黙ってセットを上書きするのは、便利さより事故のほうが大きく、
作業結果を見て保存するかどうかを決めるのは Live の前に座っている人の判断です。

### 引き換えになるもの

- Live 組み込みの Python には外部パッケージを入れられない。MCP の Streamable HTTP を標準ライブラリだけで自前実装する必要がある
- 現在の Node 実装はそのままでは使えない。ツールの仕様は流用できるが、実装は書き直し
- Remote Script は Live の UI スレッドを止めうるため、重い処理を分割する設計は引き続き必要

### 併用する経路

`.als` の直接生成は第 9 節のとおり実装・検証まで済んでいます。用途で住み分けます。

| やりたいこと | 経路 |
|---|---|
| 動いているセットを操作する（再生、パラメータ、クリップ追加） | LOM（M4L / Remote Script） |
| セットを一から組み立てる、Group 化する | `.als` の直接生成 |
| ブラウザからデバイス・プリセットを読み込む | Remote Script（`Browser.load_item`） |

`.als` 生成は動いているセットには触れません。Live が開いている `.als` を書き換えても、
メモリ上のセットは変わらず、保存時に上書きされて消えます。

## 検証は完了している

第 8 節の 6 項目はすべて実機で確認済みです。推定のまま残している項目はありません。

## この記録から残る教訓

3 段階すべてで、**「動かない」の原因が想定と違う層**にありました。
v8 はファイルがあるのに読み込まれず、js はコードが正しいのにファイルが見つからず、
保存は API が無いのではなく経路に露出していませんでした。

いずれも、エラーが出ないまま無応答になるという同じ形で現れます。
決め手になったのは推測ではなく、毎回ログとバイナリと戻り値でした。
関数一覧に無いものを実際に呼んでみるという実験をしなければ、
壁の正体は Live の制約だと誤解したままだったはずです。

もう 1 つ。**Push 3 のモデル定義を API 一覧として読んだ推定は外れました。**
それらしい根拠が出てきた時点で結論を出さず、実機で `AttributeError` を見るまで
確定としなかったことで、間違ったまま移行に入らずに済んでいます。

そして `.als` の Group トラック生成では、**Live に一度やらせて差分を取る**というやり方が、
自分では気付けなかった実装漏れ（子トラックの出力ルーティング）を捕まえました。
スキーマが公開されていない相手には、仕様を推測するより正解データを作らせる方が速くて確実です。
